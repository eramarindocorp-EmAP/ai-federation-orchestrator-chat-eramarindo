# AI Federation Messaging Protocol v1

## 1. Purpose

Define a minimal, provider-neutral envelope for messages exchanged by the orchestrator and connected agents. This is an application protocol, not a claim that model providers natively communicate with one another.

## 2. Envelope

```json
{
  "protocol_version": "1.0",
  "message_id": "uuid",
  "correlation_id": "uuid",
  "conversation_id": "uuid",
  "run_id": "uuid",
  "sender": {
    "type": "human|orchestrator|agent",
    "id": "stable-id"
  },
  "recipient": {
    "type": "agent|room",
    "id": "stable-id"
  },
  "message_type": "task|response|review|status|error",
  "created_at": "ISO-8601 timestamp",
  "content": {
    "text": "message body"
  },
  "context": {
    "source_message_ids": [],
    "attachments": []
  },
  "policy": {
    "classification": "internal",
    "max_hops": 3,
    "requires_human_approval": false
  }
}
```

## 3. Required semantics

- `message_id` uniquely identifies one message.
- `correlation_id` links related events across a run.
- `conversation_id` identifies the room conversation.
- `run_id` identifies one orchestrated execution.
- Recipient and room membership are checked server-side.
- Timestamps are UTC ISO-8601.
- Content is untrusted input, even when generated by an agent.
- Attachments must be separately authorized and scanned.
- `max_hops` and orchestrator turn limits prevent recursive loops.

## 4. Agent response contract

An adapter should normalize provider output into:

```json
{
  "agent_id": "stable-id",
  "provider": "provider-name",
  "model": "configured-model-id",
  "status": "succeeded|failed|cancelled|timeout",
  "text": "normalized response text",
  "usage": {
    "input_tokens": null,
    "output_tokens": null
  },
  "provider_request_id": null,
  "latency_ms": 0,
  "error": null
}
```

Unavailable usage fields remain null; do not invent token counts or costs.

## 5. Supported orchestration patterns

- Direct: one recipient.
- Broadcast: bounded set of recipients, concurrent calls with per-provider timeout.
- Sequential review: explicit, ordered chain with a configured maximum number of steps.
- Parallel tasks: separate scoped prompts, then an orchestrator synthesis step.
- Facilitated room: orchestrator-controlled turns, explicit stop conditions, and maximum rounds.

## 6. Failure handling

Normalize authentication, rate limit, timeout, provider unavailable, invalid response, budget exceeded, and policy denied into distinct error categories. Retry only transient errors, with capped exponential backoff and idempotency protection where supported. Never silently convert failure into a successful answer.

## 7. Security and privacy

Send each agent only the context needed for its task. Do not forward all room history or sensitive attachments by default. Respect provider data handling terms and user-selected data classification. Do not place secrets in message content.
